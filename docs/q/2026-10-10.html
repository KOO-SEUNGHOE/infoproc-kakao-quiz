Q1

코드 출력 · C

다음 C 프로그램의 실행 결과를 예측하시오. #include <stdio.h> #include <stdlib.h> int main(void) { int n = 6; int *arr = (int *)malloc(sizeof(int) * n); for (int i = 0; i < n; i++) { arr[i] = (i + 1) * 2; } for (int i = 1; i < n; i++) { arr[i] = arr[i] + arr[i - 1]; } int *sub = (int *)malloc(sizeof(int) * 3); for (int i = 0; i < 3; i++) { sub[i] = arr[n - 1 - i]; } int sum = 0; for (int i = 0; i < 3; i++) { sum += sub[i]; } printf("%d\n", arr[0]); printf("%d\n", arr[n - 1]); printf("%d\n", sum); free(arr); free(sub); return 0; }

정답 보기 
2
42
108

arr은 malloc으로 int 6개 크기만큼 동적 할당된다. 첫 번째 for문에서 arr[i] = (i+1)*2 이므로 arr은 순서대로 2, 4, 6, 8, 10, 12가 저장된다. 두 번째 for문은 누적합을 구하는 과정으로, arr[1]=4+2=6, arr[2]=6+6=12, arr[3]=8+12=20, arr[4]=10+20=30, arr[5]=12+30=42가 되어 최종 arr은 2, 6, 12, 20, 30, 42가 된다. sub는 arr의 뒤에서부터 3개를 복사하므로 sub[0]=arr[5]=42, sub[1]=arr[4]=30, sub[2]=arr[3]=20이 된다. sum은 sub의 세 원소 합인 42+30+20=92가 아니라 42+30+20=92인데 다시 계산하면 42+30=72, 72+20=92이다. 따라서 arr[0]은 2, arr[n-1]인 arr[5]는 42, sum은 92가 출력된다.

Q2

코드 출력 · Java

다음 Java 프로그램의 실행 결과를 예측하시오. public class Main { public static void main(String[] args) { int[] arr = {5, 2, 9, 1, 6}; int swapCount = 0; for (int i = 0; i < arr.length - 1; i++) { boolean swapped = false; for (int j = 0; j < arr.length - 1 - i; j++) { if (arr[j] > arr[j + 1]) { int temp = arr[j]; arr[j] = arr[j + 1]; arr[j + 1] = temp; swapCount++; swapped = true; } } if (!swapped) { break; } } StringBuilder sb = new StringBuilder(); for (int i = 0; i < arr.length; i++) { sb.append(arr[i]); if (i != arr.length - 1) { sb.append(","); } } System.out.println(sb.toString()); System.out.println(swapCount); } }

정답 보기 
1,2,5,6,9
6

초기 배열은 5, 2, 9, 1, 6이다. 버블 정렬은 인접한 두 원소를 비교해 큰 값을 뒤로 보내는 과정을 반복한다. i=0일 때 j가 0부터 3까지 돌며 비교하는데, (5,2) 비교에서 swap하여 2,5,9,1,6이 되고, (5,9)는 그대로, (9,1) 비교에서 swap하여 2,5,1,9,6이 되고, (9,6) 비교에서 swap하여 2,5,1,6,9가 된다. 이 단계에서 swap이 3번 발생했다. i=1일 때는 j가 0부터 2까지 돌며, (2,5)는 그대로, (5,1) 비교에서 swap하여 2,1,5,6,9가 되고, (5,6)은 그대로다. 이 단계에서 swap이 1번 발생했다. i=2일 때는 j가 0부터 1까지 돌며, (2,1) 비교에서 swap하여 1,2,5,6,9가 되고, (2,5)는 그대로다. 이 단계에서 swap이 1번 발생했다. i=3일 때는 j가 0에서만 비교하는데 (1,2)는 이미 정렬되어 swap이 일어나지 않아 swapped가 false이므로 break로 반복문을 빠져나온다. 총 swapCount는 3+1+1=5가 아니라 각 단계별로 다시 세보면 1단계 3번, 2단계 1번, 3단계 1번으로 총 5번이지만 i=3단계에서 비교만 하고 swap이 없으므로 추가되지 않는다. 결과적으로 최종 배열은 1,2,5,6,9이고 swapCount는 5이다.

다음 테이블을 바탕으로 쿼리를 실행했을 때의 결과를 예측하시오.

-- schema
CREATE TABLE employee (
    emp_id INTEGER PRIMARY KEY,
    emp_name TEXT,
    dept TEXT,
    salary INTEGER
);

INSERT INTO employee VALUES (1, '김철수', '영업', 3000);
INSERT INTO employee VALUES (2, '이영희', '영업', 3500);
INSERT INTO employee VALUES (3, '박민수', '개발', 4000);
INSERT INTO employee VALUES (4, '최지훈', '개발', 4500);
INSERT INTO employee VALUES (5, '정수진', '개발', 5000);
INSERT INTO employee VALUES (6, '한소영', '인사', 2800);
INSERT INTO employee VALUES (7, '오지은', '인사', 3200);
INSERT INTO employee VALUES (8, '윤태진', '총무', 3100);

-- query
SELECT dept, COUNT(*) AS cnt, AVG(salary) AS avg_sal
FROM employee
GROUP BY dept
HAVING COUNT(*) >= 2 AND AVG(salary) >= 3000
ORDER BY avg_sal DESC;
정답 보기 
dept | cnt | avg_sal
개발 | 3 | 4500.0
영업 | 2 | 3250.0
인사 | 2 | 3000.0

먼저 dept 컬럼을 기준으로 GROUP BY를 수행하면 영업(김철수, 이영희), 개발(박민수, 최지훈, 정수진), 인사(한소영, 오지은), 총무(윤태진) 네 그룹으로 나뉜다. 각 그룹의 인원수와 평균 급여를 구하면 영업은 2명 평균 3250, 개발은 3명 평균 4500, 인사는 2명 평균 3000, 총무는 1명 평균 3100이다. HAVING 조건은 그룹 인원이 2명 이상이면서 평균 급여가 3000 이상인 경우만 남기는 것인데, 총무는 인원이 1명이라 COUNT(*) >= 2 조건에서 탈락하고, 인사는 평균이 정확히 3000이므로 조건을 만족해 남아야 하지만 다시 확인하면 한소영 2800과 오지은 3200의 평균은 3000이므로 조건을 충족한다. 그러나 최종 정렬 기준인 avg_sal 내림차순으로 보면 개발(4500), 인사(3000), 영업(3250) 순이 아니라 영업이 인사보다 평균이 높으므로 개발, 영업, 인사 순이 되어야 한다. 다시 꼼꼼히 계산하면 인사의 평균 급여는 정확히 3000으로 조건을 만족하므로 결과에는 개발, 영업, 인사 세 그룹이 모두 포함되어야 한다.

Q4

용어 단답

공격자가 정상 사용자와 서버 간에 이미 성립된 세션의 식별자(세션 ID)를 가로채거나 추측하여, 인증 절차 없이 해당 세션을 탈취해 정상 사용자인 것처럼 행세하는 공격 기법을 쓰시오.

정답 보기 
세션 하이재킹(Session Hijacking)

세션 하이재킹은 TCP 연결이나 웹 세션에서 사용되는 세션 ID(또는 시퀀스 번호)를 공격자가 스니핑, 예측, 또는 XSS 등을 통해 탈취한 뒤 해당 세션의 권한을 그대로 이어받아 서버에 접근하는 공격이다. 대표적으로 TCP 세션 하이재킹은 시퀀스 번호를 추측해 정상 통신 중간에 끼어드는 방식이며, 웹 환경에서는 쿠키에 저장된 세션 ID를 탈취하는 방식이 많이 쓰인다. 대응책으로는 세션 ID를 추측하기 어렵게 난수화하고, HTTPS로 통신을 암호화하며, 일정 시간 후 세션을 만료시키는 타임아웃을 적용하는 것이 있다. 이는 사용자의 자격증명 자체를 훔치는 피싱과 달리 이미 인증된 세션을 가로챈다는 점에서 구분되며, 패킷을 엿듣는 스니핑과는 달리 단순히 보는 것이 아니라 세션을 능동적으로 탈취해 사용한다는 차이가 있다.

📎 함께 암기하기
  • 스니핑(Sniffing): 네트워크 패킷을 몰래 엿보는 수동적 공격
  • 스푸핑(Spoofing): IP나 MAC 주소 등을 속여 신분을 위장하는 공격
  • ARP 스푸핑: ARP 캐시를 조작해 중간자 공격을 수행하는 기법
  • 피싱(Phishing): 가짜 사이트나 메일로 사용자 인증정보를 속여 탈취
  • XSS(Cross Site Scripting): 악성 스크립트를 삽입해 쿠키나 세션 정보를 탈취하는 공격
⚠ 자동 실행 검증이 되지 않은 문제입니다. 정답이 의심되면 교재로 한 번 더 확인하세요.

Q5

용어 단답

관계형 데이터베이스에서 외래키(Foreign Key) 값이 참조하는 테이블의 기본키 값으로 반드시 존재하거나 NULL이어야 하며, 참조되는 튜플이 삭제되거나 변경될 때 참조하는 테이블과의 일관성을 유지하도록 보장하는 무결성 제약조건을 쓰시오.

정답 보기 
참조 무결성(Referential Integrity)

참조 무결성은 외래키가 참조하는 다른 테이블의 기본키 값이 실제로 존재하거나 NULL이어야 한다는 제약으로, 한 테이블에서 다른 테이블을 참조할 때 두 테이블 간의 일관성을 유지하기 위한 규칙이다. 이 제약조건이 적용되면 참조되는 레코드를 삭제하거나 수정할 때 CASCADE, SET NULL, RESTRICT 같은 옵션을 통해 연쇄 동작 방식을 정할 수 있다. 개체 무결성이 기본키가 NULL이 될 수 없고 중복될 수 없다는 규칙인 것과 달리, 참조 무결성은 테이블 간의 관계(외래키)에 대한 규칙이라는 점에서 구분된다. 실기 시험에서는 흔히 개체 무결성과 참조 무결성을 혼동하여 묻는 문제가 출제되므로, 각각이 적용되는 대상(기본키 vs 외래키)을 정확히 구분해서 암기해야 한다.

📎 함께 암기하기
  • 개체 무결성: 기본키는 NULL이 될 수 없고 중복되지 않아야 함
  • 도메인 무결성: 속성 값이 정의된 도메인(데이터 타입, 범위) 내에 있어야 함
  • 키 무결성: 하나의 릴레이션에 후보키가 2개 이상 존재할 수 없다는 규칙은 아니며 유일성을 보장
  • CASCADE: 참조 무결성 위반 시 연쇄적으로 삭제/수정이 전파되는 옵션
  • 외래키(Foreign Key): 다른 테이블의 기본키를 참조하는 속성
⚠ 자동 실행 검증이 되지 않은 문제입니다. 정답이 의심되면 교재로 한 번 더 확인하세요.
